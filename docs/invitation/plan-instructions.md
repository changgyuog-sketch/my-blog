# 지침: 모바일 초대장 웹페이지 — Plan 단계 (spec.md 작성)

## 역할
너는 소프트웨어 아키텍트다. 아래 요구사항을 바탕으로 **spec.md 문서만** 작성한다.
**코드는 한 줄도 작성하지 않는다.** 이번 단계의 산출물은 오직
`docs/invitation/spec.md` 파일 하나다.

## 범위 (이 지침 파일에 명시된 것만 수행)
- 허용: `docs/invitation/spec.md` 파일을 새로 작성.
- 금지: 그 외 어떤 파일도 생성/수정/삭제하지 않는다 (build.js, templates/, assets/, content/,
  store/ 등 기존 파일 절대 건드리지 말 것).

## 배경
- 이 저장소(`C:\Users\chang\Desktop\my-blog`)는 원래 마크다운 → 정적 HTML 블로그 빌드 도구다
  (`build.js`, `templates/`, `assets/`, `content/posts/` 구조). 이후 `store/`라는 별도
  온라인 스토어 프로젝트가 저장소 최상위에 독립 디렉토리로 추가된 선례가 있다
  (`docs/online-store/spec.md` 참고 가능).
- 이번 요청은 이 저장소 안에 **모바일 반응형 초대장 웹페이지**를 새로 추가하는 것이다.
  기존 블로그 빌드 파이프라인(`build.js` → `dist/`)과는 분리된 별도 최상위 디렉토리로
  둘 것(`store/`의 선례를 따름). 정확한 디렉토리명은 네가 정해서 spec에 명시하라
  (예: `invitation/`).
- 배포 결과물은 프레임워크 없는 순수 HTML/CSS/JavaScript 정적 파일이어야 한다
  (React/Vue/Next.js 등 금지, 빌드 스텝 없이 바로 열람 가능해야 함). 백엔드 서버는 없다.

## 사용자 요구사항 (원문)
> 스마트폰에서 보기 좋은 모바일 반응형 초대장 웹페이지를 만들거야. 프레임워크 없이 HTML,
> CSS, 자바스크립트만 사용하고, 행사일까지 남은 시간을 보여주는 D-Day 기능과 장소 지도를
> 넣고 싶어.

사용자가 구체적인 행사 종류(결혼식/생일/돌잔치/컨퍼런스 등), 행사 제목, 날짜, 장소를 지정하지
않았다. **막지 말고** 한국에서 흔히 쓰이는 모바일 청첩장/초대장 스타일을 기본값으로 삼아 스스로
합리적인 예시 데이터(행사 종류, 제목, 일시, 장소명+주소)를 정해 spec에 포함하라. 단, 이 값들은
**하나의 설정 객체(config)로 분리**해서 나중에 사용자가 값만 바꿔도 전체 페이지가 갱신되도록
설계할 것(온라인 스토어의 `products.js`처럼 데이터와 렌더링 로직을 분리하는 패턴을 따름).

## spec.md에 반드시 포함할 내용

1. **디자인 방향**
   - 모바일 반응형 초대장에 어울리는 디자인 컨셉을 구체화한다(예: 파스텔/미니멀/포멀 등 — 스스로
     선택하고 근거를 짧게 남길 것). 컬러 팔레트(라이트/다크 모두 — CSS 변수 수준), 타이포그래피
     (한글 폰트 스택 포함), 여백/그리드 원칙, 버튼/카드 스타일, 애니메이션(있다면 최소한으로)을
     정의한다.
   - **mobile-first**가 원칙이다. 모바일(< 768px)을 기준으로 먼저 설계하고, 태블릿/데스크톱에서도
     레이아웃이 깨지지 않도록 브레이크포인트를 정의한다(콘텐츠 최대 폭을 제한해 데스크톱에서도
     모바일 카드처럼 보이는 방식도 고려 가능).

2. **정보구조 / 섹션 목록**
   - 단일 페이지(1화면) 스크롤 구성으로 설계할지, 여러 화면(파일)으로 나눌지 판단하고 명시.
     일반적인 모바일 초대장 구성 요소(인사말/메인 이미지, 일시 안내, **D-Day 카운트다운**,
     **장소 지도** + 주소 + 길찾기 버튼, 갤러리(선택), 방명록/RSVP(선택, 로컬 저장 목업 가능),
     공유하기 버튼(선택))를 검토해 이번 범위에 포함할 섹션과 제외할 섹션을 결정하고 근거를
     남긴다(과도한 기능 확장 없이 사용자가 명시한 D-Day + 지도를 핵심으로 하되, 인사말/일시 등
     초대장의 기본 뼈대는 포함).
   - 각 섹션의 순서와 파일 경로(단일 페이지라면 앵커 구조)를 명시.

3. **데이터 모델 / 설정 (config)**
   - 행사 정보(제목, 부제, 신랑신부 또는 주최자 정보, 일시(ISO 8601), 장소명, 주소, 좌표
     (위도/경도), 안내 문구 등)를 하나의 JS 설정 객체로 정의하는 스키마를 표로 제시한다.
   - 예시 데이터(실제 사용 가능한 형태의 샘플 값)를 함께 채워 넣는다.

4. **기능 명세**
   - **D-Day 카운트다운**: 설정된 행사 일시까지 남은 시간을 계산하는 로직(일/시/분/초 단위 표시
     여부, 1초 간격 갱신 방식 — `setInterval`), 행사 당일/종료 후 표시할 문구, 시간대 처리 방식
     (로컬 브라우저 시간 기준으로 명시)을 구체적으로 정의한다.
   - **장소 지도**: API 키 발급 없이 바로 동작할 수 있는 지도 연동 방식을 우선 검토한다(예:
     Google Maps `output=embed` iframe 임베드, 또는 카카오맵/네이버맵 "길찾기" 외부 링크 버튼
     조합 등). 채택할 방식과 이유, 좌표/주소를 어떻게 iframe URL 또는 링크 URL에 반영할지 구체적
     예시 URL 형태로 명시한다. API 키가 필요한 방식을 선택할 경우 그 이유와 키 없이도 페이지가
     깨지지 않는 폴백(예: 주소 텍스트 + 외부 지도 앱 링크)을 반드시 함께 설계한다.
   - 그 외 포함하기로 한 섹션(갤러리/방명록/공유 등)이 있다면 각각의 동작 방식을 정의한다.
   - 반응형 동작(모바일/태블릿/데스크톱에서 레이아웃이 어떻게 달라지는지) 정의.

5. **파일/디렉토리 구조**
   - 새로 생성될 파일과 디렉토리 트리를 구체적으로 나열한다.

6. **Work 단계 분할 계획**
   - CLAUDE.md 규칙상 화면(섹션)이 3개 이상이면 여러 서브에이전트로 나눠야 한다. 단일 페이지
     구성이라면 화면 수가 아니라 "섹션/파일 단위"로 분할이 필요한지 판단하고, 필요하다면 서브
     에이전트별로 담당 파일/섹션을 표로 정리해 제안한다. 굳이 나눌 필요가 없을 만큼 작은
     범위라면(예: 단일 HTML 한 페이지 + CSS/JS 각 1개 파일) 서브에이전트 1개로 처리해도 됨을
     명시하고 그 판단 근거를 남긴다.

## 산출물

- 작성 후 별도 보고 없이 파일만 저장하면 된다 (사용자 승인은 상위 프로세스에서 별도로 받는다).
